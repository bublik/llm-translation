# AGENTS.md

Локальні правила для Codex у цьому репозиторії (`speech_translate_service`).

## 1) Мова, комунікація, коміти

1. Усі пояснення, summary змін і commit messages писати українською.
2. Не виконувати `git commit` без явного дозволу користувача.
3. Перед можливим комітом показувати `git diff --stat` і короткий перелік змін.
4. У фіналі кожної задачі давати стислий звіт у форматі:
   - Що змінено
   - Чому
   - Ризики
   - Що не перевірено

## 2) Код-стандарти (Python/FastAPI)

1. Нові/змінені методи мають мати короткий docstring (призначення, ключові параметри, return).
2. Для публічних методів/endpoint handlers обовʼязково описувати неочевидні параметри та сайд-ефекти.
3. Використовувати type hints для всіх нових публічних функцій.
4. Не змішувати функціональні зміни з великим рефакторингом в одному кроці без потреби.

## 3) API-контракт і сумісність

1. Якщо змінюються ендпоінти, схеми запитів/відповідей, валідація або коди помилок:
   - оновити `docs/openapi.json`;
   - оновити приклади в `docs/translator_api.http` (якщо файл існує).
2. Для кожної API-зміни в summary явно писати:
   - що змінилось;
   - чи є breaking changes;
   - як мігрувати клієнта.
3. Не робити “тихих” поведінкових змін: у звіті вказувати old/new поведінку.

## 4) Моделі та інференс (NLLB/AR->RU)

1. Значення за замовчуванням (model id, beam size, max tokens, batch size, device) мають бути централізовані в конфігурації.
2. Зміни дефолтів інференсу обовʼязково документувати в `README.md` і `.env.example`.
3. Для помилок інференсу додавати структуровані поля діагностики (`reason`, `model`, `device`, `latency_ms`, `job_id`).
4. Для GPU-шляху передбачати fallback/помилку з чітким повідомленням, без «мовчазного» деградування якості.

## 5) Тести (обовʼязково)

1. Кожна функціональна зміна повинна мати або оновлені, або нові тести.
2. Для багфіксу додавати мінімум:
   - тест, що відтворює баг;
   - тест на виправлену поведінку.
3. Після змін запускати релевантні тести локально і повідомляти результат.
4. Якщо тести не запущені, явно вказувати причину.

## 6) Docker, runtime, конфігурація

1. Для нових env-параметрів оновлювати:
   - `.env.example`
   - `README.md`
2. Для runtime-змін (порт, healthchecks, worker mode, model cache path) оновлювати docker-конфіг і документацію в одному change set.
3. Не додавати секрети в репозиторій.

## 7) Спостережуваність

1. Логи мають бути структурованими і без дублювання.
2. Мінімальні поля для логів запитів перекладу: `request_id/job_id`, `src_lang`, `tgt_lang`, `segments`, `model`, `device`, `latency_ms`, `status`.
3. Для помилок обовʼязково писати клас помилки і короткий `reason`.

## 8) Планування змін

1. Для змін, що зачіпають критичний пайплайн або більше 3 файлів, перед редагуванням дати короткий план кроків.
2. Якщо під час роботи виявлено неочікувані сторонні зміни, зупинитись і уточнити у користувача як діяти далі.

## 9) Як просити Codex про паралельну роботу

Щоб підвищити продуктивність, у задачі явно розділяти незалежні підзадачі, наприклад:
- API
- model runtime
- тести/документація

У фіналі зводити результат в єдиний summary і список змінених файлів.
